# 品牌资产与审核流程

适用：content-os-pilot 及明确的客户变体。必要输入：客户/租户、角色、资产或工单、当前结果和目标；核对实际分支、端口、数据库与媒体存储，不能把默认 main 当成本地最新客户实现。

## 方法

1. 读当前 AGENTS、文档入口、CONTEXT 和架构 ADR；复现用户真实路径。业务、审核与权限由 Django/PostgreSQL 负责，Next 只做 UI 与薄 BFF。
2. 复用当前 AssetVersion、Annotation、ReviewRound 等领域对象和服务，先核对源码名称与实现。工单受理、内容审核、入库/发布分别使用现有状态机；不以“审核通过”默认替代全部入库条件。
3. 上传或 AI 任务卡住，沿资产/版本 → 预检或 Job → Outbox → 匹配 Worker/Beat → UI 状态追踪；先找真正阻塞点，不先要求用户重传，也不跳过安全检查。
4. 新客户差异使用已存在的配置、品牌/行业包和扩展点。身份、租户和文件对象权限由后端验证；不相信客户端任意 tenant/actor，也不回退到旧 SQLite/Node 业务库。

## 验收与恢复

按任务跑需求/上传 → 提审 → 意见/退回 → 修订版 → 终审 → 入库 → 检索/下载的有关闭环，核对下载文件和已获批版本一致。覆盖允许角色、拒绝角色、跨租户或对象范围、关键异常与旧数据保留。

复用项目规定的本地验证脚本；仅重启时执行必要就绪检查，不自动全量测试、迁移或 seed。Mock/本地 Provider 与真实 OSS/Provider、生产和客户验收分别记录。权限、资源或凭据不足时保持失败关闭并给出缺失条件，不伪造成功状态。
